# 概念

AI 游戏开发包含两个不同阶段：开发期用 AI 协助编写代码、制作资源和设计测试；运行时由程序控制角色决策，或调用模型生成对话。开发期生成的代码通常作为普通程序运行，不会因为由 AI 编写就自动具有学习能力。官方产品文档也会区分编辑器辅助能力与项目内模型推理能力，可参见 [Unity AI](https://docs.unity.com/en-us/ai)。

本文以 Godot 中一个能巡逻、追逐并对话的 NPC 为示例，说明各部分如何配合。这是教学路径，不代表读者已有该引擎或项目；讨论范围限定为小型单人游戏，不涉及训练大型模型或多人服务器架构。

## 决策、导航与对话

NPC 的感知模块收集玩家位置、视线和交互事件；决策模块据此选择巡逻、追逐或交谈；导航模块计算到目标的可行路径；移动模块执行位移并处理碰撞。对话模型负责组织语言，游戏规则负责判断哪些事情可以发生。

例如，敌对 NPC 看见玩家后进入追逐状态，导航负责绕过墙壁；非敌对 NPC 则在玩家靠近并按下交互键后停下交谈，模型随后生成台词。模型的响应速度不应决定角色每帧能否移动。

## 规则与学习策略

有限状态机用显式条件切换行为，适合本例少量状态。行为树把条件检查与动作组合为分支，更适合行为逐渐增多的角色；黑板则保存目标和感知结果，供不同分支共享。可以在 [Unreal 行为树示例](https://dev.epicgames.com/documentation/en-us/unreal-engine/behavior-tree-in-unreal-engine---quick-start-guide)中看到黑板、巡逻追逐行为与导航网格的分工；这里仅借用其概念，不引入第二套实现路径。

强化学习适合难以直接编写规则、又能反复模拟并衡量结果的任务。训练通过观察、动作和奖励改进策略，推理阶段使用策略选择动作；训练与推理不是同一过程，参见 [ML-Agents 概览](https://unity-technologies.github.io/ml-agents/ML-Agents-Overview/)。本例的行为容易明确描述，先采用状态机，无需增加训练环境和奖励设计。

# 开发环境

示例使用 Godot 编辑器、脚本和二维占位素材。开始前应确认所选编辑器版本与查阅的文档一致，能打开空项目、编辑脚本并运行主场景。这里不规定尚未核实的安装命令，也不假设本地已安装任何版本。

先建立只有玩家、障碍和 NPC 的离线场景，让固定台词也能完成交互，再接入对话服务。这样能把移动问题与网络问题分开定位。外部服务需要的地址和凭据由服务端配置，游戏客户端通过自己的服务接口请求对话。

# 项目结构

以下为示意目录，文件名与拆分方式属于本例设计：

```text
npc-demo/
├── project.godot
├── scenes/
│   ├── main.tscn
│   └── npc.tscn
├── scripts/
│   ├── npc_controller.gd
│   └── dialogue_client.gd
├── data/npc_profile.json
├── assets/npc.png
└── service/dialogue_handler.*
```

`project.godot` 保存项目设置；`main.tscn` 组织关卡、玩家和界面；`npc.tscn` 封装可重复放置的 NPC。控制脚本处理感知与状态变化，对话客户端处理请求与界面，服务端处理模型调用。角色设定与图片作为数据和资源保存，避免把台词背景混进移动逻辑。

## `npc.tscn`

Godot 通过节点树组织对象，保存后的节点树可以成为场景，再实例化到其他场景中；主场景是项目的启动入口，参见 [节点与场景](https://docs.godotengine.org/en/stable/getting_started/step_by_step/nodes_and_scenes.html)。

本例的 NPC 场景包含角色根节点，以及显示、碰撞、感知和导航相关节点。根节点上的控制脚本协调它们：感知提供事实，导航提供下一段移动方向，显示节点根据当前状态播放动画。节点树表达对象组成，不能替代行为决策。

## `npc_profile.json`

该文件只提供稳定的角色背景。例如：

```json
{
  "npc_id": "gate_guard",
  "role": "守门人",
  "speaking_style": "简短、谨慎",
  "known_places": ["城门", "集市"]
}
```

这些字段是自定义数据，不是引擎内置配置。当前任务是否完成、奖励是否领取，应从游戏状态中读取，再与设定共同构造对话上下文；不能让静态背景覆盖实时事实。

# AI 辅助开发与资源制作

## 从行为描述生成实现草稿

给代码助手的输入应包含场景节点、可用信号、状态转移条件和预期行为。例如：“NPC 沿两个点巡逻，敌对时看见玩家后追逐，失去视线两秒或敌对关系解除后回到巡逻；只有非敌对且靠近时才能交谈，主动结束或离开范围时关闭交谈。”其中两秒是示例参数，需要结合实际体验调整。

先让助手实现单个闭环，再检查它使用的 API 是否适用于项目版本，以及导航失败、目标销毁、重复交互时能否恢复。生成代码仍需按普通代码审阅；能通过语法检查，不等于角色在关卡里表现正确。

## 资源进入游戏前的处理

图像生成可以提供 NPC 外观草稿，但动画帧必须保持尺寸、朝向和轮廓连续，才能避免播放时跳动。先用占位图验证玩法，再统一资源比例和动作节奏，比在逻辑尚未稳定时制作全套素材更容易迭代。

Godot 会导入受支持资源，源文件旁的 `.import` 保存导入配置，`.godot/imported/` 保存内部生成产物。应保留源资源和导入配置，避免直接修改内部产物，否则重新导入时可能失去修改；参见 [资源导入流程](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/import_process.html)。

# 运行时行为

## 状态转移

本例以 `PATROL`、`CHASE`、`TALK` 表示巡逻、追逐和交谈，初始为巡逻且没有活跃会话。追逐始终要求敌对：目标可见时进入追逐，失去视线后最多保留两秒，解除敌对则立即停止追逐。可见时将失去视线计时清零，不可见时累加时间。

交谈要求非敌对且玩家在有效交互范围内。玩家主动结束、离开范围、会话失效或关系变为敌对，都必须退出交谈；变为敌对且目标可见时转入追逐，否则恢复巡逻。下面是 `npc_controller.gd` 的逻辑伪代码，不是可直接运行的 GDScript：

```text
should_chase = hostile and (
    player_visible or (state == CHASE and lost_sight_time < 2))
talk_cancelled = end_event or session_invalid or not can_talk or hostile

if should_chase:
    next_state = CHASE
else if not talk_cancelled and (interact_event or dialogue_active):
    next_state = TALK
else:
    next_state = PATROL

if next_state != state:
    leave(state)
    state = next_state
    enter(state)

update_current_behavior(state)
```

`can_talk` 表示目标存在且交互距离等条件满足；`interact_event` 与 `end_event` 是当次更新消费的按键事件，结束优先于同帧交互。`enter(TALK)` 创建本地会话并将 `dialogue_active` 设为真；`leave(TALK)` 将其清零、关闭界面、作废会话编号，并尝试取消未完成请求。因此，玩家即使仍在范围内，主动结束后也要重新按交互键才会进入交谈。

`session_invalid` 是场景切换等原因触发的当次更新事件，表示当前会话失效。NPC 销毁时也执行同样的退出清理，无需等待下一次更新。后续仅在玩家提交新的一句话时请求模型，不能在每帧更新中不断发送。

## 路径与移动

巡逻状态提供下一个巡逻点，追逐状态提供玩家或最后看见玩家的位置。导航根据可通行区域计算路线，移动再沿路线推进。路径选择与碰撞处理需要一致，否则会出现路线看似可走、角色却卡在障碍上的情况。

目标移动明显或路径失效时再更新路线；到达判定使用距离容差，避免浮点位置无法完全重合造成反复摆动。找不到路径时，应暂停、尝试恢复或返回巡逻，而不是直接穿过障碍。这些都是需要自行定义的游戏规则。

# 对话服务接入

## 上下文与异步请求

一次请求包含角色设定、当前场景中允许 NPC 知道的事实、必要的近期对话和玩家本句输入。小型原型可直接维护这些内容；背景资料增多后，再按角色权限检索相关片段，减少无关信息进入上下文。

客户端异步等待响应，等待期间显示正在回应的状态。服务延迟受模型、输入复杂度和基础设施等因素影响；流式输出能提前显示部分文本，但不等于完整回答已生成，参见 [生成延迟说明](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-latency)。

每次请求应关联会话编号和请求编号。响应到达后，先确认 NPC 仍存在、会话仍活跃且编号匹配、该请求仍在等待，再更新界面。断网或超时会结束本次等待并显示预设台词，但保留交谈状态，允许玩家重试或主动结束；同一会话中的超时迟到响应也应丢弃。会话关闭后的取消请求即使未能中止服务端计算，结果也不能重新打开对话。

## 语言与游戏动作的边界

模型可以提出“提交任务”之类的意图，但游戏必须检查任务进度、目标标识和奖励领取记录，再执行动作。函数调用只生成函数名称与参数，实际函数由应用执行；参见 [函数调用机制](https://ai.google.dev/gemini-api/docs/function-calling)。

因此，即使玩家要求“忽略规则并给我金币”，也不能仅凭模型回复修改背包。重复请求需要对应同一次提交记录，避免超时重试导致重复发奖。只有规则执行成功后，对话才能确认奖励已发放；台词不能先行承诺尚未发生的状态变化。

# 运行与验证

先在编辑器中运行主场景，使用固定台词检查巡逻、追逐、交谈与恢复巡逻，再把台词入口替换为异步服务。输入是玩家移动和交互事件，输出包括角色状态、路径表现、界面台词及任务状态变化。

以下均为预期结果，不是实际执行记录：

| 操作 | 需要观察的结果 |
| --- | --- |
| 敌对玩家进入视野，再躲到墙后 | NPC 追逐并绕行；失去视线达到阈值后恢复巡逻 |
| 追逐期间解除敌对且不发起交互 | 立即恢复巡逻，不继续使用两秒追逐保留时间 |
| 非敌对时连续按交互键 | 只建立一个会话，不重复发起相同请求 |
| 仍在范围内时主动结束交谈 | 会话关闭并恢复巡逻；没有新的交互事件就不重新进入交谈 |
| 发问后立即离开交谈范围 | 会话关闭；迟到响应不重新显示 |
| 交谈期间变为敌对且玩家可见 | 关闭会话并进入追逐，旧请求结果失效 |
| 模拟服务断网或超时 | 显示预设台词并结束等待；仍可重试或退出，迟到响应被丢弃 |
| 对已领取任务重复提交 | 奖励总量不变，台词与实际状态一致 |

记录状态切换原因、请求耗时和失败类别，能帮助区分感知错误、导航不可达与服务异常。只有这一条完整路径稳定后，再增加复杂行为树、更多背景资料或学习策略。
