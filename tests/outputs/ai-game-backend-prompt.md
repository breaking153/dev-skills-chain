# 概念

AI 游戏开发包含开发期辅助和游戏运行时决策。前者帮助人制作游戏，后者在玩家游玩时影响角色行为。本文围绕一个能巡逻、追逐并对话的 NPC，选择 Godot 作为示例引擎；讨论技术如何协作，不创建项目。示例目录、行为优先级与阈值都是教学设计，具体引擎版本未确认。

## 开发期辅助

AI 可以帮助拆解玩法、解释代码、起草脚本或生成资源候选。例如先描述“玩家离开后，NPC 不应继续显示旧回复”，再要求 AI 列出需要保存的会话状态与边界情况。开发者要检查生成内容是否符合项目接口，并通过场景验证效果；一段看似完整的代码不代表已经运行正确。

## 运行时 AI

运行时需要区分感知、决策、导航和对话。感知回答目标在哪里、是否可见；决策选择巡逻、追逐或交谈；导航计算可达路线；语言模型生成语句或提出有限动作意图。把这些职责分开，可以在更换模型时保留既有移动和战斗逻辑。

学习型代理是另一条实现路线：把环境描述为观察、动作和奖励，通过训练得到策略，再在游戏中推理动作。[ML-Agents 概述](https://unity-technologies.github.io/ml-agents/ML-Agents-Overview/) 本例的三种行为边界清晰，先用状态机即可；只有规则难以表达且收益明确时，再评估训练成本。

# 开发环境

若后续实现，需要 Godot 编辑器、可编辑脚本的工具和一个便于重复验证的测试场景。先确认所用 Godot 版本，再查对应版本的节点与导航接口；本文不列未经版本核对的安装命令或可直接运行的 API 示例。

最初可以用固定台词或本地响应替身模拟模型。这样无需等待网络，就能检查开始会话、退出、超时和旧响应处理；待角色行为稳定后，再接入真实服务。

# 项目结构

Godot 节点组成树，保存后的节点树可以成为场景，场景又能被实例化。主场景承担项目启动入口。[节点与场景](https://docs.godotengine.org/en/stable/getting_started/step_by_step/nodes_and_scenes.html)

下面按职责拆分一个示意工程：

```text
game/
├── scenes/
│   ├── World.tscn
│   └── NPC.tscn
├── scripts/
│   ├── npc_controller.gd
│   └── dialogue_client.gd
├── data/
│   └── npc_profiles.json
└── assets/
```

## World.tscn

世界场景放置地图、玩家、NPC 实例和巡逻点。地图提供空间约束，巡逻点提供行为目标；二者改变后都可能影响路线是否可达。

## NPC.tscn

NPC 场景集中组织角色表现、碰撞和感知所需节点。`npc_controller.gd` 统一维护行为状态并下达移动目标，具体决策见[运行时行为](#运行时行为)。`dialogue_client.gd` 处理异步请求与结果分发，不直接改写追逐状态。

## npc_profiles.json

示例文件保存角色称呼、公开背景与回退台词。任务是否完成、奖励是否领取属于当前游戏事实，应从游戏状态读取，不能仅凭角色描述或历史聊天推断。私密剧情与密钥不应进入玩家可读取的公开配置。

# 资源制作

先用占位贴图和简短音效验证角色行为，再替换成正式资源，可以降低返工成本。AI 生成的素材仍需检查尺寸、风格、透明背景与使用许可；替换动画时要核对朝向和状态切换是否一致。

Godot 会导入受支持资源，源资源旁的 `.import` 保存导入配置，`.godot/imported/` 保存内部产物。应围绕源素材与导入设置管理资源，而非把内部产物当作编辑源文件。[资源导入流程](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/import_process.html)

# 运行时行为

## 感知与状态决策

示例状态机只有 `PATROL`、`CHASE`、`TALK`。每次更新先读取目标、距离、可见性与会话状态，再确定当前行为。巡逻点和玩家位置都是移动目标，状态机决定使用哪个目标，导航负责计算路径，移动执行层处理速度和碰撞。

### 巡逻与追逐

巡逻时依次前往路径点，到达后切换下一个。发现满足敌对条件的玩家时进入追逐；失去视线后保留短暂追踪窗口，窗口结束仍未重新发现目标则返回巡逻。加入时间窗口可减少边缘遮挡造成的频繁状态切换。

目标可见与路径可达是两件事。玩家跨到不可达区域时，应限制重算频率并设置放弃条件，不能每帧请求昂贵的路径计算，也不能用直线位移绕过碰撞。

### 与对话的关系

玩家进入交谈范围后，只有非追逐且允许交谈的 NPC 才进入 `TALK`。示例优先级是受击或危险事件高于对话，对话高于巡逻；进入对话会停止巡逻移动，受击则中断会话并追逐。结束交谈后重新计算移动目标，避免沿用进入会话前已经失效的路径。

以下是逻辑伪代码，未绑定具体 Godot API，也未运行：

```text
如果发生危险事件：
    使当前会话失效，进入追逐
否则如果存在有效会话：
    停止移动，保持对话
否则如果存在可追逐目标：
    更新追逐目标
否则：
    选择下一巡逻目标
```

# 对话服务

## 请求与响应

请求包含 NPC 身份、玩家输入、当前会话编号、请求编号和必要的游戏状态摘要。模型调用异步进行，界面显示等待提示；玩家离开或 NPC 受击后，会话立即失效。收到结果时先核对编号，过期响应直接丢弃，避免上一段对话覆盖当前内容。

生成延迟受模型、提示复杂度和基础设施影响。流式输出可以提前显示部分文字，首 token 时间可以衡量开始显示的等待，但它不等于整次请求耗时。[延迟说明](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-latency) 超时后使用预设台词，并保证玩家能继续操作。

## 游戏动作与权限

普通回复只作为文字显示；需要发奖或推进任务时，让模型提出结构化意图，由应用执行校验。函数调用并不是模型直接执行游戏函数，应用仍需处理参数验证、错误和认证。[函数调用](https://ai.google.dev/gemini-api/docs/function-calling)

例如 `claim_reward` 意图必须经过任务完成条件、奖励白名单和重复领取检查，通过后才更新游戏状态。公开在线游戏应由可信服务确定关键奖励结果；客户端文本和模型说法不能作为授权依据。若使用托管模型服务，服务密钥保存在服务端，客户端通过受控接口请求，接口同时限制输入长度、频率和等待时间。

# 运行与验证

按“固定台词 → 响应替身 → 真实服务”的顺序验证，便于定位行为逻辑和网络问题。下表是预期验收结果，没有实际执行记录。

| 场景 | 应观察到的结果 |
| --- | --- |
| 玩家远离 NPC | 按顺序巡逻，移动受碰撞约束 |
| 发现玩家后失去视线 | 开始追逐，超出追踪窗口后回归巡逻 |
| 对话中受击 | 会话失效，移动切换到追逐 |
| 旧响应晚到或服务超时 | 不覆盖当前会话，能退出并显示回退台词 |
| 重复提交领奖意图 | 奖励最多发放一次，失败有明确原因 |

调试时记录行为切换原因、会话编号、请求耗时与失败类别。先观察卡顿来自感知、路径计算还是网络等待，再决定优化对象；无需一开始就引入复杂训练或分布式服务。
