# 概念

AI 游戏开发涉及代码生产、运行时决策和模型训练三个不同过程。开发期用 AI 生成 NPC 脚本，得到的仍是需要检查和运行的程序；角色是否具备学习能力，取决于游戏是否另外建立训练与策略更新机制，而不是代码由谁编写。

运行时 AI 根据当前游戏状态选择行为，可以使用人工规则、状态机、行为树或训练后的策略。学习型代理需要定义观察、动作与奖励，通过训练获得策略，再用策略进行推理；推理本身不代表角色在游玩期间持续学习。[学习代理概述](https://unity-technologies.github.io/ml-agents/ML-Agents-Overview/)

本文以 Godot 中能巡逻、追逐并对话的 NPC 为示例，用规则控制行动，用语言模型生成对话。目录与状态设计仅用于解释，具体引擎版本未确认，未创建项目或执行示例。

# 项目结构

Godot 用节点树组织对象，保存的节点树可以成为场景，场景又能被实例化。[节点与场景](https://docs.godotengine.org/en/stable/getting_started/step_by_step/nodes_and_scenes.html) 下列示意组成把移动、网络请求和玩法状态分开：

```text
game/
├── scenes/
│   ├── World.tscn           # 地图、玩家与巡逻点
│   └── NPC.tscn             # NPC 的表现、碰撞与感知
└── scripts/
    ├── npc_controller.gd    # 行为协调
    ├── dialogue_client.gd   # 会话与请求管理
    └── game_actions.gd      # 玩法动作与状态更新
```

场景提供空间和对象，行为控制器读取感知结果并选择行动。对话客户端只提交请求、接收回复；改变金币、背包或任务进度的操作统一经过动作执行器。由此，模型服务可以替换，游戏规则仍由同一套确定的代码执行。

# 运行时协作

## 行为控制器

感知生成目标位置、距离和可见性等信息；状态机或行为树利用这些信息决定当前行为；导航计算到目标的可达路线；移动代码再沿路线调整位置并处理碰撞。行为树组织决策顺序与条件，本身不是寻路算法。选中追逐目标后仍可能无路可走，因此需要独立处理导航失败。

示例使用巡逻、追逐和对话三个状态。巡逻时轮流选择路径点，发现敌对玩家后转为追逐；持续失去目标达到设定时间后返回巡逻。玩家在可交谈范围内发起互动，且 NPC 当前允许交谈时，进入对话并停止巡逻移动。

这些行为共享目标和状态信息，但不必交给同一个模型。示例由控制器统一决定优先级：危险事件可以中断对话，正常交谈优先于巡逻。对话结束后重新选择当前可达目标；路径失败时限制重试并回退，避免角色卡住或穿墙。具体感知范围和等待时间属于玩法参数。

## 对话客户端

模型请求与游戏更新以不同节奏运行。客户端异步发送玩家输入及必要的 NPC 背景，等待期间继续处理输入、渲染和行为更新，并显示等待提示。避免在每帧更新中阻塞等待网络结果，是保持游戏响应的关键。

流式输出能提前显示已生成的文字，但不消除网络和模型计算延迟。首 token 时间衡量开始返回文字的等待，完整响应耗时则反映请求结束所需时间。[生成延迟](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-latency)

### 会话与请求生命周期

会话表示玩家与 NPC 的一段交互，请求表示其中一次生成。每次请求保存会话编号和请求编号；收到结果时，只有编号仍对应当前有效请求，才允许显示文字或提交动作意图。

退出会话和请求超时有不同含义。玩家主动关闭、离开范围或 NPC 受击时，会话结束，界面关闭，未完成请求失效。超时表示某次请求未在期限内完成，可以使该请求失效、显示回退台词，同时保留仍可继续的会话；玩家随后可以重试或退出。

本地取消不保证远端计算立即停止，所以还要拦截晚到结果。重试生成新请求编号，旧响应即使最后成功返回，也不能覆盖新回复。以下为未运行的逻辑示意：

```text
收到结果：
    若会话已关闭，丢弃结果
    若请求不是当前有效请求，丢弃结果
    否则显示回复，并将动作意图交给游戏规则校验
```

## 动作执行器

模型输出分为自然语言和可选的结构化意图。自然语言用于交流，不能直接作为金币已增加或任务已完成的事实。函数调用提供函数名称与参数，实际执行仍由应用负责，并需要验证请求、处理错误和身份认证。[函数调用](https://ai.google.dev/gemini-api/docs/function-calling)

例如模型提出领取奖励，动作执行器先检查玩家、任务完成条件、奖励类型和是否已经领取，再更新游戏状态。重复提交必须返回相同结果或明确拒绝，不能重复发奖。在线游戏应由可信服务掌握关键奖励状态，客户端传来的聊天文本不能授予权限。

显示“领取成功”应以动作执行结果为依据：校验失败就展示失败原因，提交成功后再反馈结果。若动作已经提交，而会话随后关闭，关闭界面不会自动撤销奖励；晚到网络回包也不得再次执行同一动作。这使对话生命周期与玩法提交边界保持清楚。

# 运行与验证

先用固定回复验证行为，再用能模拟延迟、超时和重复结果的响应替身检查对话流程，最后接入真实服务。以下为验收预期，未实际执行：

| 验证场景 | 预期行为 |
| --- | --- |
| 巡逻中发现目标，随后目标不可达 | 切换追逐，导航失败后按规则回退 |
| 等待回复时玩家退出或 NPC 受击 | 会话失效，晚到回复不显示 |
| 请求超时后玩家重新发送 | 旧请求失效，新请求可以正常完成 |
| 模型宣称已发奖或重复提交领奖 | 以游戏状态为准，奖励最多提交一次 |

记录状态切换原因、会话与请求编号、耗时和动作执行结果，便于把感知、移动、网络与规则校验的问题定位到各自职责中。
